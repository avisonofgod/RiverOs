Revisión de RiverOs

RiverOs es una base OpenWrt muy minimalista para el MikroTik hEX RB750Gr3, orientada a ejecutar NARA como gestor ISP. La separación entre el sistema operativo —RiverOs— y la aplicación —NARA-MIPS— es una buena decisión arquitectónica: permite actualizar cada capa de forma independiente y mantiene el sistema base pequeño.

Puntos positivos
Objetivo bien definido: está diseñado específicamente para el hEX RB750Gr3, MT7621, MIPS, 256 MB de RAM y 16 MB de flash.
Separación de responsabilidades: RiverOs proporciona kernel, red, arranque e imagen; NARA proporciona la lógica ISP.
Imagen reducida: eliminar LuCI, uhttpd, rpcd, cron y otros componentes reduce consumo y superficie de ataque.
Documentación operativa útil: el README describe:
nombres de interfaces;
IP inicial;
paquetes de cada variante;
proceso de construcción;
recuperación mediante netboot;
relación con NARA.
Plan de recuperación: documentar un flujo de rollback mediante initramfs es importante en un dispositivo con poco almacenamiento.
Uso de DSA: la referencia al switch MT7530 y al puerto CPU muestra que el proyecto está intentando trabajar con la arquitectura moderna de red de OpenWrt.
Riesgos críticos
1. La contraseña de root está expuesta

El README publica:

text
root: rbadmin2026

Aunque indica que debe cambiarse, la contraseña no debería estar incluida en el repositorio ni dentro de una imagen distribuible. Cualquier imagen creada desde ese estado puede quedar con credenciales conocidas.

Recomendación:

eliminar la contraseña del README;
no incluir una contraseña fija en files/etc/shadow;
generar la contraseña durante la instalación;
forzar cambio en el primer arranque;
deshabilitar el acceso SSH de root por contraseña y usar claves públicas;
añadir una comprobación en el build que rechace contraseñas predeterminadas.
2. La configuración de red manual aumenta mucho el riesgo

El proyecto deshabilita netifd, firewall, odhcpd y otros servicios, y configura la red mediante scripts init.d. Esto puede ser válido para una imagen altamente controlada, pero introduce varios problemas:

pérdida de conectividad si el orden de arranque cambia;
ausencia de validación declarativa de la configuración;
dificultad para aplicar cambios sin reiniciar;
riesgo de dejar interfaces sin protección;
mayor complejidad para integrar VLAN, bridges, mwan o WireGuard;
problemas si NARA cambia una interfaz mientras otro script la está configurando.

La decisión de renombrar interfaces durante el arranque es especialmente delicada. El propio README reconoce que hacerlo en vivo puede eliminar la IP de la interfaz. Sería preferible:

mantener nombres estables y documentados;
usar identificadores persistentes o una capa de abstracción;
ejecutar el renombrado antes de cualquier servicio que dependa de esas interfaces;
bloquear cambios concurrentes con flock;
verificar que cada interfaz existe antes de modificarla;
abortar de forma segura si el renombrado falla;
conservar temporalmente una interfaz de recuperación.
3. Falta de firewall por defecto

Eliminar el firewall puede ser peligroso en un equipo que expone servicios como SSH, el portal en el puerto 80 y la administración en el 8081. Si NARA no instala reglas antes de levantar la red, el router podría arrancar con servicios accesibles desde todas las interfaces.

Como mínimo, la imagen base debería:

aceptar tráfico local;
permitir SSH únicamente desde la interfaz de administración;
restringir el puerto 8081;
bloquear tráfico entrante no solicitado en interfaces externas;
separar claramente tráfico de gestión, clientes y uplinks;
aplicar reglas antes de iniciar NARA.

Si se utiliza nftables, conviene que exista un conjunto mínimo de reglas de emergencia incluso cuando NARA todavía no esté instalado.

4. Build aparentemente poco reproducible

El README incluye hashes MD5 y menciona artefactos locales en rutas como:

text
/root/netinstall-openwrt/backups/

Eso dificulta reproducir el binario en otra máquina. El proyecto debería fijar explícitamente:

versión exacta de OpenWrt;
versión del ImageBuilder;
arquitectura y target;
lista completa de paquetes;
contenido exacto de files/;
opciones de compilación;
versión de scripts;
checksum SHA-256, no solo MD5.

Sería recomendable publicar un script de build idempotente que ejecute algo equivalente a:

sh
set -eu
umask 077

y que falle si faltan archivos, si el checksum no coincide o si se detecta una credencial por defecto.

5. El README mezcla estados y variantes

Se describen varias imágenes:

NETEST;
NARA-BASE;
NARA-RADIUS;
NARA-RADIUS-EMBEBIDO;
una imagen GOOD.

Pero no queda completamente claro:

qué variante es la recomendada;
qué paquetes contiene exactamente cada una;
si NARA está incluido o se instala después;
qué imagen es adecuada para producción;
qué imagen puede actualizarse mediante sysupgrade;
qué configuración se conserva durante una actualización.

Conviene añadir una tabla de variantes:

Variante	Incluye	Uso	Tamaño	Recomendación
NETEST	Sistema mínimo	Pruebas	—	Desarrollo
NARA-BASE	Sistema + red/firewall/WireGuard	Instalación normal	—	Recomendado
NARA-RADIUS	Base + PPP/PPPoE/RADIUS	ISP con autenticación	—	Casos específicos
NARA-RADIUS-EMBEBIDO	NARA integrado	Instalación cerrada	—	Producción controlada

También sería importante publicar los tamaños reales de las imágenes y el espacio libre tras la instalación.

Observaciones de mantenibilidad
Scripts de arranque

Los scripts deberían seguir una estructura defensiva:

sh
#!/bin/sh /etc/rc.common
START=98
USE_PROCD=1

Y deberían incluir:

validación de dependencias;
mensajes claros en el log;
comprobación de interfaces;
comportamiento idempotente;
limpieza de estado anterior;
códigos de salida correctos;
stop_service funcional;
protección contra ejecuciones simultáneas.

Los comandos de red no deberían ejecutarse silenciosamente. Por ejemplo, conviene registrar si ip link set, ip addr add o la configuración del switch fallan.

Configuración

configs/ y overlay-backup/ parecen servir como referencias y snapshots, pero sería útil distinguirlos claramente:

configuración fuente;
archivos generados;
respaldos históricos;
archivos que realmente entran en la imagen.

Un snapshot completo del overlay puede incluir accidentalmente:

claves privadas;
hashes de contraseñas;
identificadores del dispositivo;
configuraciones específicas de una instalación;
logs o archivos temporales.

Debería añadirse un proceso automático que revise secretos antes de cada commit.

Compatibilidad con NARA

La dependencia con NARA es fuerte: RiverOs elimina componentes estándar y espera que NARA gestione interfaces, VLAN, bridges, mwan y WireGuard. Esto debe formalizarse con un contrato de integración:

versión mínima y máxima de NARA;
interfaces que RiverOs garantiza;
servicios que NARA puede iniciar o detener;
formato de configuración;
orden de arranque;
comportamiento cuando NARA no está instalado;
mecanismo de actualización y rollback;
API o comandos disponibles para configurar la red.

En su estado actual, instalar RiverOs sin NARA parece dejar un sistema deliberadamente incompleto, por lo que el README debería advertirlo de forma más visible.

Seguridad de la cadena de arranque y actualización

El proceso sysupgrade PLAIN y la recuperación mediante netboot deberían documentarse con más precisión. Faltan detalles como:

cómo se verifica la imagen antes de instalarla;
si existe firma criptográfica;
qué ocurre ante una interrupción eléctrica;
si se conserva o borra la configuración;
cómo se detecta una imagen incompatible;
cómo se valida que el dispositivo es realmente el modelo esperado.

MD5 no debería utilizarse como mecanismo de autenticidad. Como mínimo:

publicar SHA-256;
firmar manifiestos o imágenes;
verificar la firma antes de sysupgrade;
incluir el target y la revisión del hardware en el nombre de la imagen.

Además, la dirección MAC concreta del dispositivo no debería estar en un repositorio público salvo que sea estrictamente necesaria. Para documentación, sería mejor sustituirla por una dirección ficticia.

Prioridad de mejoras
Eliminar la contraseña predeterminada y cualquier secreto del repositorio.
Añadir firewall mínimo antes de iniciar servicios.
Proteger los scripts de red contra fallos, carreras y cambios de nombres incompletos.
Hacer el build reproducible y usar SHA-256 o firmas.
Separar claramente configuración fuente, snapshots y archivos generados.
Documentar el contrato RiverOs–NARA.
Añadir pruebas automatizadas para arranque, interfaces, rollback y generación de imágenes.
Publicar tamaños, paquetes exactos y procedimiento de instalación por variante.
Evaluación general

La idea es sólida y el repositorio tiene una dirección técnica clara: un OpenWrt reducido, especializado y controlado por una aplicación externa. Sin embargo, todavía parece más un sistema de laboratorio o una base interna que una distribución lista para despliegues masivos. Los mayores bloqueadores para producción son la credencial fija, la ausencia de firewall base, la configuración de red mediante scripts frágiles y la falta de un proceso de build y actualización verificable.

Valoración aproximada: 6/10 como prototipo técnico; 3–4/10 como imagen lista para producción, principalmente por seguridad operativa y mantenibilidad, no por la arquitectura general.
