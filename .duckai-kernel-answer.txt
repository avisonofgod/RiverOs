3. Riesgos técnicos detectados
A. Confusión entre DSA, switch CPU y nombres de interfaz

La afirmación:

text
eth0..eth4 = ether1..ether5 + sw0 CPU interno

debe verificarse en el sistema real. En DSA, el puerto CPU no suele ser un puerto Ethernet normal que deba exponerse o configurarse como un puerto físico. El nombre exacto puede variar entre kernel, DTS y versión de OpenWrt.

Hay que documentar el resultado de:

bash
ip -br link
ls -l /sys/class/net
for i in /sys/class/net/*; do
    echo "=== $i"
    cat "$i/address" 2>/dev/null
    readlink "$i/device" 2>/dev/null
done


dmesg | grep -Ei 'dsa|mt7530|mt7621|ethernet|mdio'

Y comprobar cada puerto con un cable y enlace físico:

bash
ethtool eth0
ethtool eth1
ethtool eth2
ethtool eth3
ethtool eth4

No debe confiarse únicamente en el orden de enumeración eth0, eth1, etc.

B. Red manual sin netifd

Deshabilitar network, firewall y odhcpd puede ser válido para un appliance muy controlado, pero aumenta mucho el riesgo operativo:

No hay gestión declarativa del estado.
No hay rollback automático.
Los reinicios pueden dejar interfaces sin dirección.
El firewall puede desaparecer completamente.
El gestor Risp y riveros-red pueden tener carreras de arranque.
El comportamiento tras una actualización es más difícil de predecir.

Especialmente peligroso es deshabilitar firewall mientras se utilizan chains NAT del gestor Risp. Es necesario demostrar quién crea, carga y mantiene las reglas nftables.

Inspecciones mínimas:

bash
nft list ruleset
ip rule
ip route
ip -d link
logread

Mi recomendación es no reactivar todo necesariamente, pero sí sustituir los scripts SysV por servicios procd con:

respawn
dependencias explícitas
validación de interfaces
timeout
rollback
logs claros

Paso 10: usar el initramfs 22.03.3 como rescate

El procedimiento debe ser:

Preparar un host Linux aislado.
Conectar físicamente el host al puerto que el bootloader utilice para Etherboot.
Configurar DHCP/TFTP únicamente sobre esa interfaz.
Servir el initramfs-kernel conocido de OpenWrt 22.03.3.
Configurar RouterBOOT temporalmente para arrancar por Ethernet una vez.
Arrancar el hEX sin escribir NAND.
Verificar que el kernel recuperador ve la NAND y la red.
Desde ese entorno, transferir la imagen candidata.
Volver a arrancar por NAND solo después de validarla.

La idea esencial es que el initramfs de recuperación se ejecuta en RAM y no depende de que la imagen instalada sea arrancable. Procedimientos de netboot para este modelo usan DHCP/BOOTP/TFTP y un initramfs-kernel.bin; también se recomienda separar el ordenador de recuperación del equipo utilizado para la configuración del router.

Paso 14: prueba de rollback

El rollback debe ser un procedimiento documentado:

text

2. Preparar DHCP/TFTP con initramfs 22.03.3.
3. Configurar Etherboot temporal.
4. Arrancar en RAM.
5. Confirmar que la placa responde.
6. Escribir la imagen estable conocida.
7. Arrancar desde NAND.
8. Restaurar únicamente configuración validada.

No considerar terminado el proyecto hasta haber ejecutado este rollback con éxito.

Eliminar la contraseña fija.
Retirar cualquier clave privada del repositorio.
Crear un procedimiento de netboot probado.
Verificar la MAC y el puerto de recuperación.
Añadir SHA-256.

Convertir los scripts en paquetes:

El primer hito serio no es “compila el kernel 6.12.94”. Es este:

Desde un checkout limpio y un commit conocido, RiverOs genera una imagen initramfs que arranca por TFTP, una imagen sysupgrade válida para RB750Gr3, reproduce el comportamiento de red esperado y puede volver atrás mediante el initramfs 22.03.3.

Hasta alcanzar ese punto, modificar drivers o el DTS sería aumentar el riesgo sin disponer de una cadena de recuperación y auditoría suficientemente sólida.
